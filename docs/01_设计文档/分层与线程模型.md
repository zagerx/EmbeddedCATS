# 分层与线程模型

本文件定义目录、依赖和线程契约。修改后运行 `firmware/apps/tools/layering_check.sh` 自检。

## 一、目录职责

| 目录 | 职责 | 允许依赖 |
|---|---|---|
| `third_party/CANopenLinux/` | 上游 SocketCAN、epoll、错误处理与 CANopenNode | 上游依赖；源码只读 |
| `canopen/master/` | 主站生命周期、节点表、NMT、心跳与通信复位 | CANopenLinux、CANopenNode |
| `canopen/transport/` | `sdo_access` 对象访问契约及同线程 SDO 后端 | 契约无依赖；后端依赖 CANopenNode |
| `cia402/` | DS402 标准知识与单从站运行控制 | `sdo_access`、`hsm`；PDS 纯知识无依赖 |
| `axis/` | 单位换算、轴命令与反馈；每轴持有一条 SDO 通道 | `cia402`、`canopen/transport` |
| `states/` | 整机业务状态图与状态注册表 | `hsm`、`axis`；外部动作只经 `controller_*` |
| `hsm/` | 通用层次状态机内核 | 无 |
| `controller/` 根 | 装配、生命周期、事件循环、命令与快照 | 上述各层公共接口 |

`config/` 保存机械参数与 CANopen 对象字典，不是独立业务层。

`struct controller` 持有主站指针和轴集合，每轴 SDO 通道内嵌于 `axis`。HSM、输入队列
与状态字段平铺在控制器中。主站实例由 `controller.c` 静态持有并原地初始化；`states/`
不接触主站头部。CAN 接口、socket、epoll、timerfd、eventfd 和动态协议对象均由下层
管理，宿主不再打开或保存 fd。

## 二、依赖方向

```text
control ──> states ──> axis ──> cia402/device ──> cia402/pds
   │                                    │
   │                                    └──> sdo_access <── canopen_sdo ──> CANopenNode
   ├──────> canopen_sdo
   └──────> canopen/master ──> CANopenLinux ──> SocketCAN / epoll
```

- `cia402/pds.c` 及其公共类型不依赖传输、线程、时钟或单位。
- `cia402/device*.c` 只依赖 `sdo_access`，不得 include CANopenNode 或线程、epoll 头。
- 只有主站、SDO 后端、对象字典和第三方源码可以 include CANopenNode/CANopenLinux 头。
- 任何下层不得 include 上层；UI 不知道 fd、CAN 帧、对象字典或 CiA402 内部对象。

## 三、单工作线程模型

`controller/` 不创建线程。Qt 为 UI 线程加一个 CANopen 工作线程；`master_probe` 的
主线程本身就是该工作线程。

| 线程 | 调用 / 职责 | 跨线程边界 |
|---|---|---|
| CANopen 工作线程 | init、CAN 收发、SDO、CiA402、整机状态机 | 独占全部协议与设备对象 |
| UI / 外部调用方 | 命令、状态与故障查询 | 带锁命令队列、发布快照、eventfd |

每轮顺序固定：

```text
CO_epoll_wait()
→ CO_epoll_processRT(false)
→ 各轴 sdo_client_step(dt_us, &timerNext_us)
→ CO_epoll_processMain(false, &reset)
→ 各轴 axis_poll()
→ controller_poll()
→ CO_epoll_processLast()
```

CAN 帧和 eventfd 会提前唤醒；基础定时器保留 1 ms，用于超时和反馈调度。SDO 使用
epoll 的真实时间差，不假定每轮恰好 1 ms。`CO_epoll_processMain()` 已包含
`CO_process()`，其他位置不得重复调用。

### 硬规则

1. CANopenNode、CANopenLinux、NMT 与 SDO 只由 CANopen 工作线程访问。
2. CiA402 请求、流程状态与反馈不再跨服务/I/O 线程，不使用设备互斥锁。
3. UI 命令入队后写 eventfd；停止和急停保持队头优先规则。
4. UI 只读控制层发布快照，不直接读取设备或协议对象。
5. 收到本机通信复位时重建协议服务，保留 `CO_t` 和 SDO 客户端地址。

### 生命周期

```text
controller_init(ifname)
→ 工作循环
→ 停止标志
→ eventfd 唤醒
→ join
→ controller_deinit()
→ CO_CANmodule_disable() / CO_delete() / CO_epoll_close()
```

所有初始化返回值必须检查；失败逆序释放已建资源。重复初始化返回状态错误，重复
`controller_deinit()` 不重复关闭资源。队列和快照使用静态互斥锁，重复装配只复位数据。

### 超时

- SDO 协议超时由 `CO_SDOclientUpload()` / `CO_SDOclientDownload()` 按真实时间差推进。
- CiA402 另有单笔事务、步骤、运动和停止期限，由工作线程时钟管理。
- 宿主的定时周期不负责解释设备超时。

## 四、分层检查

| 规则 | 判据 |
|---|---|
| R1 | CiA402 纯 PDS 不出现 CANopen、传输或 COB-ID 依赖 |
| R2 | `apps/` 不接触 CANopen 驱动、协议类型或 SocketCAN |
| R3 | CANopenNode/CANopenLinux 头只用于主站、SDO 后端、对象字典和第三方源码 |
| R4 | 命令和业务状态机无阻塞调用 |
| R5 | 项目代码不直接包含 SocketCAN 头，不再保留 `bus/` 或 `canopen/driver/` |
| R6 | 整机状态机不出现协议对象号、主站或下层私有头 |
| R7 | HSM 不出现业务类型与词汇 |
| R8 | `controller/` 项目代码不创建线程 |
| R9 | CANopenLinux 与嵌套 CANopenNode 均无本地源码改动 |
| R10 | 主站不出现 CiA402 或业务依赖 |
| R11 | CiA402 不依赖线程、epoll 或协议栈 |

纯注释行不计为依赖。规则需要随目录契约同步更新，不能通过排除本项目代码掩盖违规。

## 五、验收

```bash
cmake -S firmware -B firmware/build
cmake --build firmware/build -j4
./firmware/build/cia402_selftest
firmware/apps/tools/layering_check.sh
python3 firmware/apps/tools/fake_drive/selftest.py
```

端到端验证需要先配置 `can0` 主站与 `can1` 模拟从站，待模拟器启动后运行：

```bash
python3 firmware/apps/tools/fake_drive/fake_drive.py -i can1 -n 1,2 &
timeout 20 firmware/build/master_probe can0 6 \
  --move 5 --move-at 1000 --stop-at 1200 --estop-at 1800
```

期望状态流：`PREPARING → CONFIGURING → IDLE → ENABLING → HOLDING → MOVING →
HALTING → HOLDING → ESTOP`。其中 `IDLE` 是“已配置、未使能”的空闲态，`master_probe`
在进入它时自动下发一次使能请求（`--no-enable` 可关掉，用于验证停在空闲）。软件模拟
不等同于真实驱动器上的时序与运动安全确认。
